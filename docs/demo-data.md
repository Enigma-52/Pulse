# Demo / test telemetry (`pulse/cmd/loadgen`)

`loadgen` synthesizes a realistic e-commerce topology so every dashboard screen
has lifelike data locally. Run it against a running Pulse:

```bash
cd pulse
go run ./cmd/loadgen                 # backfill 45m of history, then stream live
go run ./cmd/loadgen -backfill 120   # backfill 2h
go run ./cmd/loadgen -once           # backfill only, then exit
```

It emits **11 services** across **production/staging**, with correlated traces,
logs, and metrics: nested spans with a sequential (cascading) waterfall, HTTP
routes/status codes, DB client spans, external API calls, exception events, and
per-service CPU/memory/request/latency metrics.

## ⚠️ Simulated, not real instrumentation — left to test

All of the following is **generated by loadgen**, not captured from real
systems. The shapes match the OTel semantic conventions Pulse parses, but the
end-to-end path from a *real* instrumented dependency has **not** been verified:

- **Databases page** (`postgresql`, `redis`, `mongodb`): derived from synthetic
  `db.system` / `db.statement` client spans. No real database is queried.
- **External APIs page** (`api.stripe.com`, `api.ups.com`): synthetic HTTP
  client spans, not real outbound calls.
- **Metrics** (`system.cpu.utilization`, `http.server.request.duration`, …):
  synthetic gauge/sum/histogram points, not a real host/runtime exporter.
